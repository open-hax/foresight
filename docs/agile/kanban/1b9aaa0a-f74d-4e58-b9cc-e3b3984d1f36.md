# Put a Representation provider boundary above the markup AST

Server-side rendering is not a CMS capability, and naming the operation
"rendering" would smuggle in the assumption that the only output is a visual one.
The stable concern is representation: expressing a semantic artifact concretely,
through a replaceable provider.

```text
semantic artifact
      → representation provider
      → HTML / React tree / Markdown / PDF / feed / plain text
```

Representation works better as an axis than as the name of a class. Concrete
implementations stay locally named — `:representation/react-ssr` — rather than
encoding the whole taxonomy into every identifier.

## Existing foundation

`uxx-shared-markup-html-helix-renderers` already landed the primitive worth
having: a portable markup AST, a React-free HTML renderer, and a Helix adapter.
That work is valid and this card does not reopen it. The `hiccup-vs-helix` note
settled the question underneath it — SSR reuses the existing Helix frontend
rather than introducing a second HTML DSL. This card is only the
provider/operation boundary sitting above those implementations.

## Scope

- A representation provider protocol taking a resolved semantic or view artifact
  and emitting a concrete representation.
- React SSR as the first provider, over the existing AST.
- One non-visual provider described — Markdown or plain text is enough — to keep
  the boundary honest about not being a renderer interface.

## Non-goals

- Not resource persistence, publication intent, or transduction.
- Not a new markup DSL. If this card produces one, it has gone wrong.
- Not a decision about which frontend framework the client uses. The point of
  the boundary is that this stops being a coupled question.

## Done when

- The same resolved artifact renders through two providers, at least one of them
  not producing HTML.
- The provider boundary names no CMS, no publication concept, and no framework
  in its contract.
- A consumer chooses a representation without knowing where the artifact came
  from — EDN repository, Optimizely, or generated.
- **Something calls it in production**, not only tests.
