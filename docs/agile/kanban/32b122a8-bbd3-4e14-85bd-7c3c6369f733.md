# Model the four capabilities as typed steps and find the facet that is missing

Both notes that produced this decomposition end on the same next move, and it is
a probe rather than a build. From
`naming-operation-categories-repository-transduction-evaluation-representation.md`:

> Define a **Step contract** with four things first: `operation`, `requires`,
> `provides`, and `traits`. Then model the current CMS → translation → SME
> review → SSR flow entirely as composable steps and see whether any edge
> requires knowledge that isn't expressed in those contracts. That missing
> knowledge will tell us what the next facet/category needs to be.

That contract now exists. Katamorph #6 (typed action ports, `:step/in` dataflow)
and #7 (portable condition kernel) are merged; #8 validates composition and #10
proves structural port compatibility. So the probe is executable, and it is
cheap compared to building four capabilities and discovering the cut was wrong.

This card builds nothing. It writes the existing flow as Katamorph step data and
reports what the type system cannot say.

## Why this is first

The Knoxx publication epic decomposed cleanly, produced twelve well-tested
cards, and still delivered a library with no caller — because nothing checked
that the pieces composed before they were built. A decomposition that type-checks
on paper is the cheapest available evidence that these four boundaries are real.

## Scope

- Express the existing Knoxx flow — resource read, translation, SME review,
  HTML output — as `Repository -> Transduction -> Evaluation -> Representation`
  steps in Katamorph's action/step vocabulary.
- Use the real contracts already in the tree where they exist: the publication
  resource laws, `translation_config`, the review surface, and the uxx markup AST.
- For every edge, state what the downstream step needs and whether
  `requires` / `provides` / `traits` can express it.
- Record every edge that needs out-of-band knowledge. Those are the findings.

## Non-goals

- No new capability implementation.
- No new DSL. If a facet is missing, name it; do not design it here.
- No change to the four capability epics already written in Knoxx PR #238
  (`knoxx-resource-repository-cms`, `knoxx-transduction-provider-pipeline`,
  `knoxx-evaluation-review-system`, `knoxx-representation-output-boundary`).
  Those stay the reference statements of intent.

## Done when

- The whole four-stage flow exists as step data that Katamorph's validator
  accepts, or the validator's rejection is itself the finding.
- Every edge that needs knowledge outside `operation` / `requires` / `provides` /
  `traits` is listed with the concrete thing it needed.
- Any place where one responsibility lands in two boxes is named — per the note,
  that is where the next boundary gets cut.
- The output is a short written finding, linked from this card, that the four
  capability cards can be re-scoped against.
