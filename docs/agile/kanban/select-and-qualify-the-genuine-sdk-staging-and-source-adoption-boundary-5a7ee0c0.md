# Select and qualify the genuine SDK staging and source-adoption boundary

## Outcome

Before EC1.02 implementation/readiness, select one usable Knoxx-owned route that
materializes the complete retained hot and supported graph obligations through
SDK `07085d6557b75834ce6f50e6c54b8ca47e1c7c08`, preserves historical production
sources, and exposes every newly generated source fact for separate admission.
Deliver the reviewed interface and a recoverable actual-SDK fixture proof; an
unsupported/refusal-only design does not complete the required cutover.

## Scope and dependencies

This is a bounded Knoxx design/prototype prerequisite, parallel to EC1.01's
validated runtime. EC1.02 (`11bc1411-154d-4db7-8c27-51506ab30508`) depends on
this UUID and EC1.01 (`d3277a3c-6e30-42b1-8151-16c041612a6a`). It has no production-deploy
or product-proof prerequisite. Its controlled provider fixture proves SDK
transformation/persistence custody only; EC1.01 separately qualifies the actual
Qwen/1024 provider and every future writer/query path.

Pinned SDK exports no standalone whole-graph input transform. Its genuine
`ingestEvents` operation admits base events and can emit derived events, graph
edges, labels and vectors. Evaluate the isolated staging-database route without
copying internal semantics or replaying historical events into production.
Bind a complete immutable retained-source snapshot, a distinct staging database,
actual SDK/runtime hashes, and every generated source/projection identity.
Establish graph source-family and ordinary-event-derived graph closure, hydration,
existing-ID conflicts and the supported transfer/adoption boundary.

Discovery freezes a complete proposed append delta. A separately identified
accepting authority/channel must authorize its exact hash, source/output IDs,
snapshot, database, controller/caller, run and attempt before production adoption.
The generator and apply process cannot accept their own output. Define the
verified decision input and refusal behavior; this planning card chooses no
future accepted source/controller or currently active admission mechanism.

## Acceptance criteria

- [ ] A reviewed source-family/output map and interface cover the real observed
  312 hot-eligible/424 graph.node case, including graph work from ordinary events;
  fresh complete source enumeration, not those unlocked counts, determines work.
- [ ] Actual SDK fixture execution retains every base/derived event, edge, label,
  vector and partition output with its source/provenance. No fabricated append
  handles, silently dropped families or guessed projection semantics supply proof.
- [ ] A valid route resolves all supported output identities/conflicts and exposes
  new canonical facts separately from projection writes; historical production
  source IDs/bytes/history are never its admission or rollback mutation surface.
- [ ] Missing/foreign/self-issued acceptance, changed delta/snapshot/binding,
  collisions, unavailable hydration, partial generation or omitted outputs refuse
  adoption and preserve recoverable evidence. Blank text is not assumed zero work.
- [ ] The prototype proves its transfer and recovery interface on an owned fixture;
  actual production apply/verify/journal behavior remains EC1.02 scope. If current
  exports cannot support the route, retain the precise blocker and review revised
  owner scope; do not hide an SDK change or declare this prerequisite complete.

## Verification and estimate

Use the real pinned SDK operation with an owned isolated Mongo fixture and an
explicit controlled embedding provider; label it fixture evidence, not live model
qualification. Exercise hot, graph, ordinary-event-derived graph and hydrated
sources; complete output closure; existing-ID conflict; generation failure;
wrong-database transfer; and separately accepted/rejected/changed append deltas.
Bind the installed ingest module and whole generated output, not declared counters.
Run genuine Knoxx owner suites and zero-warning lint/typecheck; retain actual
commands, source/fixture hashes and outcomes. No production execution occurs
while drafting or reviewing this plan.

Five points is a proposed bound for one existing-SDK route/interface and fixture
proof. Production migration, SDK repository changes, generic graph migration and
new admission infrastructure are excluded. Split and review any independent new
scope before EC1.02's eight-point implementation estimate is accepted.
